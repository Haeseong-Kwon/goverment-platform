# 사업비 비목 룰셋 갱신 절차

「사업비 비목 해설」이 개정되면 **`src/features/expense-rules/ruleset.ts`를 사람이 고쳐야 합니다.**
자동 반영은 되지 않습니다. 이 문서는 그 이유와 손대야 할 곳을 정리합니다.

## 왜 자동이 아닌가

원본은 `developer_docs/사업비 비목 해설.pdf`입니다. PowerPoint 2019에서 내보낸 15쪽짜리
문서인데, 기계가 읽을 수 있는 글자가 거의 없습니다.

```
$ pdftotext -layout "developer_docs/사업비 비목 해설.pdf" -
# 15쪽에서 약 1.1KB만 추출됩니다 (대부분 도형·아웃라인 텍스트)
```

그래서 파싱해서 자동으로 룰셋을 만드는 경로는 처음부터 성립하지 않습니다. 지금 구조는
**사람이 읽고 `ruleset.ts`에 옮긴 표가 유일한 기계 판독 근거**이고, 엔진·AI·화면이 전부
그 파일 하나만 봅니다. 문서를 아무리 갱신해도 이 파일을 고치지 않으면 제품은 옛 기준으로
판정합니다.

## 룰셋이 흘러가는 곳

```
사업비 비목 해설.pdf  (사람이 읽음)
        │
        ▼
src/features/expense-rules/ruleset.ts     ← 유일한 근거. 여기만 고칩니다.
        │
        ├─▶ engine.ts               결정론적 판정 (최종 판정은 항상 여기서)
        ├─▶ lib/ai/rulesetBrief.ts  모델에게 넘길 요약
        │      ├─▶ expenseJudge.ts  집행 건 설명 → 비목·플래그 분류
        │      └─▶ openrouter.ts    사업계획서의 사업비 계획 점검
        └─▶ 화면                    비목 설명·유의사항·반려 안내문 인용
```

**AI는 분류만 하고 판정하지 않습니다.** 모델에게는 요약본이 가지만, 통과/보완/불가 판정은
언제나 `engine.ts`가 전체 룰셋으로 내립니다. 모델이 틀려도 판정 기준은 흔들리지 않습니다.

## 갱신 절차

### 1. 버전을 올립니다

```ts
// ruleset.ts
export const RULESET_VERSION = "bimok-2027-v1";  // 연도·개정 회차
```

이 값은 반려 안내문과 진단 화면에 그대로 찍혀 "어떤 기준으로 판정했는지"의 근거가 됩니다.
올리지 않으면 옛 기준으로 판정한 결과가 새 기준인 것처럼 보입니다.

### 2. 바뀐 내용을 해당 자리에 옮깁니다

| 개정 내용 | 고칠 곳 |
|---|---|
| 금액 기준 변경 (사전승인 한도, 멘토링 단가 등) | `POLICY` |
| 비목 신설·폐지 | `CATEGORIES` + `types.ts`의 `ExpenseCategory` |
| 집행 가능 범위·유의사항 문구 | 해당 비목의 `scope` / `cautions` |
| 집행 불가 항목 추가 | 해당 비목의 `violations` |
| 필수 증빙 변경 | 해당 비목의 `requiredEvidence` |
| 새로운 금지 항목 유형 | `ITEM_FLAG_LABELS` + `types.ts`의 `ItemFlag` |

`cautions`·`violations`는 화면에 인용되는 **설명문**입니다. 실제 판정은 `engine.ts`의
검사 함수가 하므로, 문구만 고치고 규칙을 안 넣으면 판정은 그대로입니다.

### 3. 플래그를 추가했다면 엔진에도 검사를 넣습니다

`ItemFlag`를 추가하면 AI가 그 플래그를 설정할 수 있게 되지만, `engine.ts`에 대응하는
검사가 없으면 **아무 판정도 나오지 않습니다.** 실제로 `used_item`(중고 기계·설비)이
이 상태로 방치돼 중고 기자재를 잡아내도 결과가 비어 있던 적이 있습니다.

플래그를 추가하면 다음 검사로 누락을 잡을 수 있습니다.

```bash
node -e '
const rules = require("fs").readFileSync("src/features/expense-rules/ruleset.ts","utf8");
const eng = require("fs").readFileSync("src/features/expense-rules/engine.ts","utf8");
const flags = rules.match(/ITEM_FLAG_LABELS[^=]*= \{([\s\S]*?)\n\};/)[1].match(/^  (\w+):/gm).map(s=>s.trim().replace(":",""));
const dead = flags.filter(f => !new RegExp("\\b"+f+"\\b").test(eng));
console.log(dead.length ? "엔진이 검사하지 않는 플래그: " + dead.join(", ") : "모든 플래그가 검사됩니다");
'
```

### 4. 회귀 테스트를 먼저 씁니다

`regressions.test.ts`에 **바뀐 기준으로 실패하는 테스트를 먼저 넣고**, 룰셋을 고쳐
통과시킵니다. 테스트를 나중에 쓰면 옛 기준을 그대로 굳히게 됩니다.

```bash
npm test -- src/features/expense-rules
```

규칙을 잠깐 지웠을 때 테스트가 실제로 실패하는지(RED) 확인한 뒤 되돌립니다. 실패하지
않는 테스트는 그 규칙을 검사하지 않는 것입니다.

### 5. 원본을 함께 커밋합니다

개정된 PDF를 `developer_docs/`에 갱신해 둡니다. 다음 사람이 "지금 룰셋이 어느 판을
옮긴 것인지" 확인할 수 있어야 합니다.

## 확인 체크리스트

- [ ] `RULESET_VERSION`을 올렸다
- [ ] 바뀐 금액 기준을 `POLICY`에 반영했다
- [ ] 새 플래그마다 `engine.ts` 검사가 있다 (위 스크립트로 확인)
- [ ] 회귀 테스트를 RED → GREEN으로 확인했다
- [ ] `npm test` / `npm run lint` / `npm run build` 통과
- [ ] 개정 PDF를 `developer_docs/`에 갱신했다

## 범위 밖

- 비목 판정은 **참고용**입니다. 최종 적격 여부는 공고문과 주관기관 지침을 따릅니다.
  화면 문구에서 이 경계를 지우지 마세요.
- AI 응답만으로 통과/불가를 정하지 않습니다. 판정 권한은 `engine.ts`에 있습니다.
